Lektion KM7-05 · Ausführen & Automatisieren

Das Skript, das ohne dich läuft

Console, Terminal und Rscript — wie eine Auswertung von der Kommandozeile ausgeführt wird, was der Exit-Code verrät und warum jede Automatisierung darauf aufbaut.

Lektüre

R4DS 2e (englisch), Pflicht — Kap. 6 — Workflow: scripts and projects. Das Kapitel kennst du aus KM7-04; hier geht es eine Stufe weiter: dasselbe Skript, aber ausgeführt ohne RStudio-Fenster.

Einstiegsfrage

Die Auswertung aus der letzten Lektion steht: ein Projekt pmm-km7-04, ein Skript scripts/analyse.R, drei Maschinen-Kennzahlen. Nächste Woche kommt die neue Charge — und die Produktionsleitung will dieselbe Auswertung, aber automatisch: nachts nach der Schicht, ohne dass jemand RStudio öffnet, die Datei anklickt und Ctrl + Shift + S drückt.

RStudio braucht ein Fenster, eine Maus und dich. Ein Server im Netzwerk hat keins von denen — oft nicht mal einen Bildschirm.

Was braucht ein Skript, um ohne dich zu laufen? Genau dieselbe Frage steckt übrigens hinter diesem Kurs: jedes Code-Beispiel hier wurde vor dem Druck automatisch ausgeführt und geprüft — mit genau dem Werkzeug, das du heute lernst.

Ziel-Artefakt

Das ist das Ergebnis, das du am Ende dieser Doppelstunde selbst erzeugst: derselbe Auswertungsbefehl — getippt in ein schwarzes Fenster, ohne dass RStudio überhaupt geöffnet ist.

$ Rscript scripts/analyse.R
# A tibble: 3 × 4
  maschine     n mittel      s
  <chr>    <int>  <dbl>  <dbl>
1 M1          37  10.0  0.0315
2 M2          39   9.98 0.0400
3 M3          40  10.1  0.0696

Ein Aufruf, keine Maus, keine offene Datei — die Kennzahlen sind da. Bis dahin sind es sieben Schritte, und du gehst sie in dieser Lektion selbst.

Schritt 1 — Console ist nicht Terminal

In RStudio unten links liegt die Console mit dem Prompt >: Dort ist R, du tippst Zeile für Zeile. Daneben gibt es aber ein zweites schwarzes Fenster — das Terminal. In RStudio findest du es als eigenen Tab (unten, neben der Console; oder über Tools → Terminal).

Das Terminal gehört dem Betriebssystem (Linux, Windows, macOS) — es kennt R gar nicht. Seine Aufgabe: Programme starten. Und eines der Programme, die es starten kann, heißt Rscript.

Die eine Regel

In der Console tippst du R-Befehle. Im Terminal tippst du Befehle ans Betriebssystem. Dieselben Wörter bedeuten dort etwas anderes — cd, ls (Windows: dir) sind keine R-Funktionen, und R-Befehle wie mean() versteht das Terminal nicht.

Schritt 2 — Rscript: die ganze Datei, kein Prompt

Rscript wird zusammen mit R installiert (prüfen: Rscript --version im Terminal). Es macht genau eine Sache: eine .R-Datei komplett einlesen, komplett ausführen, sich dann beenden. Kein Prompt >, kein Fenster, keine Rückfragen.

$ Rscript scripts/analyse.R
# A tibble: 3 × 4
  maschine     n mittel      s
  <chr>    <int>  <dbl>  <dbl>
1 M1          37  10.0  0.0315
2 M2          39   9.98 0.0400
3 M3          40  10.1  0.0696

Das ist dasselbe Skript aus KM7-04 — nur führt es hier der Terminal-Aufruf aus, nicht Ctrl + Shift + S in RStudio. Das Ergebnis ist identisch, weil derselbe Code auf denselben Daten läuft.

Schritt 3 — Frische Session: die Reproduzierbarkeits-Garantie

Ein Rscript-Lauf startet mit leerem Environment. Was in RStudio noch im Speicher lag — Objekte aus dem Herumprobieren, geladene Pakete, eingelesene Daten — existiert hier nicht. Das Skript muss alles selbst mitbringen: library(tidyverse) ganz oben, read_csv(...) für die Daten.

Das ist kein Nachteil, sondern die Garantie, die Automatisierung braucht: gleicher Code + gleiche Daten = gleiches Ergebnis — unabhängig davon, was vorher auf dem Rechner passiert ist. Man nennt das Reproduzierbarkeit.

Praxistest

Ein Skript, das automatisiert laufen soll, muss von null laufen — so, als hätte der Rechner gerade erst gebootet. Bewährter Test: RStudio ganz schließen, neu öffnen, Ctrl + Shift + S. Läuft es? Dann läuft auch Rscript.

Mit welchem Environment startet ein Rscript-Lauf?

Schritt 4 — Einzeiler ohne Datei: Rscript -e

Manchmal will man keine Datei anlegen, sondern nur eine einzige Sache prüfen. Rscript -e '<Ausdruck>' führt einen Ausdruck direkt aus und beendet sich:

$ Rscript -e 'mean(c(2, 4, 9))'
[1] 5
$ Rscript -e 'cat(2^10, "\n")'
1024

Nützlich für Schnellchecks — und dafür, aus anderen Systemen heraus eine kleine R-Rechnung anzustoßen, ohne eine Datei anzulegen.

Wofür ist die Option -e bei Rscript da?

Schritt 5 — Argumente von außen: commandArgs()

Ein Skript, das immer nur dieselbe Maschine auswertet, ist halb automatisch. Mit commandArgs(trailingOnly = TRUE) liest das Skript, was beim Aufruf hinter dem Dateinamen steht — so wird aus einem Skript ein Werkzeug mit Parametern:

# maschine.R — Kennzahlen fuer eine Maschine
# Aufruf: Rscript scripts/maschine.R M2
suppressMessages(library(tidyverse))

args <- commandArgs(trailingOnly = TRUE)
if (length(args) != 1) stop("Benutzung: Rscript scripts/maschine.R <M1|M2|M3>")

daten <- read_csv("data/betriebsdaten.csv", show_col_types = FALSE)

daten |>
  filter(maschine == args[1]) |>
  summarise(
    n      = sum(!is.na(masse_mm)),
    mittel = mean(masse_mm, na.rm = TRUE),
    s      = sd(masse_mm, na.rm = TRUE)
  )

Drei Dinge passieren hier: args[1] ist der erste Aufruf-Parameter (hier der Maschinenname), filter() wählt die passende Maschine aus, und stop() bricht mit einer verständlichen Meldung ab, wenn die Benutzung falsch ist:

$ Rscript scripts/maschine.R M2
# A tibble: 1 × 3
      n mittel      s
  <int>  <dbl>  <dbl>
1    39   9.98 0.0400
$ Rscript scripts/maschine.R
Error: Benutzung: Rscript scripts/maschine.R <M1|M2|M3>
Execution halted

Ein Skript, drei Maschinen — ohne den Code dreimal zu kopieren. Und der fehlende Aufruf-Parameter wird nicht stillschweigend ignoriert, sondern sauber abgefangen.

Was liefert commandArgs(trailingOnly = TRUE) in maschine.R zurück?

Schritt 6 — Der Exit-Code: was Automatisierung wirklich liest

Wenn ein Programm endet, hinterlässt es der Shell eine Zahl: den Exit-Code. 0 heißt „sauber durchgelaufen", alles andere heißt „da ist etwas schiefgegangen". Genau diese Zahl liest jede Automatisierung — ein nächtlicher Cron- Job entscheidet danach, ob er eine Mail schickt oder still weiter arbeitet.

$ Rscript -e 'stop("Datei nicht gefunden")'
Error: Datei nicht gefunden
Execution halted
$ echo $?
1

R beendet sich mit Code 1; die Shell zeigt ihn mit $? (Linux/macOS). Und wichtig: Nach dem Fehler wird nichts mehr ausgeführt — auch nicht der Rest des Skripts.

Exit-Code ≠ korrektes Ergebnis

Der Exit-Code sagt nur, dass das Skript lief — nicht, dass das Ergebnis richtig ist. Beispiel: Rscript scripts/maschine.R M4 läuft sauber durch (Exit-Code 0), gibt aber n = 0, mittel = NaN aus, weil es M4 in den Daten nicht gibt. Prüfungen wie „gibt es die Maschine überhaupt?" gehören ins Skript — z. B. mit stopifnot() oder einer eigenen if-Prüfung.

Ein nächtlicher Automatismus will wissen: War der Lauf erfolgreich? Was liest er?

Schritt 7 — Shebang: das Skript als Programm

Zeile 1 von maschine.R sieht aus wie ein Kommentar, ist aber keiner: #!/usr/bin/env Rscript ist der Shebang. Er sagt Linux/macOS: führe diese Datei mit dem Programm Rscript aus. Mit chmod +x scripts/maschine.R wird die Datei ausführbar, und danach genügt:

$ ./scripts/maschine.R M1
# A tibble: 1 × 3
      n mittel      s
  <int>  <dbl>  <dbl>
1    37   10.0 0.0315

Das Skript ist jetzt selbst ein kleines Programm. (Unter Windows funktioniert der Shebang nicht — dort ruft man Rscript direkt auf.)

Historisch: R CMD BATCH

Der ältere Vorgänger von Rscript; er schreibt eine Protokolldatei .Rout. In alten Unterlagen wirst du ihm begegnen — neuere Skripte benutzen Rscript.

Was bedeutet die Zeile #!/usr/bin/env Rscript am Dateianfang?

Typische Fehler

Fehler 1 — „Objekt nicht gefunden", obwohl es in RStudio lief

Error: object 'daten' not found

In RStudio war daten noch im Environment — von den Zeilen davor. Rscript startet leer. Lösung: alles, was das Skript braucht, steht in der Datei (library(), read_csv()). Die frische Session erzwingt Skript-Disziplin — genau das ist ihr Sinn.

Fehler 2 — Der relative Pfad gilt vom Aufruf-Ordner

$ Rscript ~/projekte/pmm-km7-04/scripts/analyse.R
Error: 'data/betriebsdaten.csv' does not exist

Du rufst von zu Hause (~) auf — dann sucht R data/ in ~, nicht neben dem Skript. Relative Pfade gelten vom Arbeitsverzeichnis des Aufrufs, nicht vom Ordner der Skript-Datei. Lösung: erst cd in den Projektordner, dann aufrufen.

Fehler 3 — Nach dem Fehler läuft nichts mehr

Error: 'data/betriebsdaten.csv' does not exist
Execution halted

Rscript bricht beim ersten Fehler ab. Steht weiter unten im Skript noch Code — z. B. write_csv() der Ergebnisse — wird er nicht ausgeführt. In der Automatisierung ist das gewollt: eine halbe Auswertung ist gefährlicher als keine.

Fehler 4 — Der Plot landet in Rplots.pdf

# ✗ erwartet: ein Plot-Fenster — gesehen: nichts

Nicht-interaktiv gibt es kein Grafikfenster; R schreibt Plots still in Rplots.pdf. In Skripten speicherst du explizit: ggsave("plots/masse.png", p). Dann weiß die Automatisierung, wo das Bild landet.

Du rufst Rscript /home/ana/projekt/scripts/analyse.R aus deinem Home-Ordner auf und bekommst 'data/betriebsdaten.csv' does not exist. Warum?
